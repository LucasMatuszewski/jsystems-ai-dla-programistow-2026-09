Dzień 2 / punkt wyjścia

Wracamy do PRD i wybieramy projekt

Wczoraj zrobiliśmy PRD. Dziś agent przechodzi przez pełny cykl: architektura → plan → implementacja → testy → pull request.

  • Możesz pracować na PRD z grupy albo wybrać własny pomysł.
  • Celem jest przejście całego procesu na małym fragmencie, nie ukończenie pełnego MVP.

Główne ćwiczenie · Przebieg dnia

01 / architektura

Agent porównuje, Ty wybierasz

  • Wyodrębnij z PRD decyzje o architekturze, bibliotekach, modelu danych i środowisku.
  • Agent sprawdza aktualną dokumentację i porównuje opcje - Ty oceniasz dowody i wybierasz.
  • Zapisz każdą decyzję w ADR przez write-adr z EdukeyTeam/agent-toolbox. Przykład: jeden ADR dla bazy danych i modelu danych, drugi dla frameworka lub biblioteki agenta AI.
  • Podaj linki do bibliotek, które rozważasz, np. Chat SDK, OpenRouter Responses API, OpenRouter z Vercel AI SDK. Bez nich agent często ich nie znajdzie i wybierze starsze wzorce. Przykładowy prompt

Z PRD i ADR do planu i macierzy zależności

Agent tworzy plan: lista zadań, kolejność, właściciele plików, testy i punkty kontroli. Ty sprawdzasz i zatwierdzasz zakres przed implementacją.

  • Zwykła sesja - też może przygotować plan; wyraźnie poproś o zatrzymanie przed implementacją.

# Plan pracy nad aplikacją na podstawie PRD

Pracuję nad projektem opisanym w aktualnym PRD. Zapytaj mnie o ścieżkę do PRD i istniejących ADR-ów, jeśli ich nie podałem. Źródłem wymagań jest **aktualny PRD mojego projektu**, nie przykładowy prompt z materiałów kursowych. Jeśli pracuję nad grupową aplikacją do obsługi zwrotów i reklamacji elektroniki, pomiń funkcje opcjonalne usunięte z PRD podczas zajęć.

Najpierw ustal stan faktyczny. Przeczytaj wskazany przeze mnie PRD, istniejące ADR-y, wytyczne projektu, README i bieżący kod. Wskaż pliki, które rzeczywiście udało Ci się otworzyć, oraz polecenia uruchomienia i testów, które da się potwierdzić. Katalog `course-materials/` zawiera materiały dydaktyczne i przykłady; nie przeszukuj go ani nie traktuj jego PRD/ADR jako dokumentacji aplikacji, chyba że wskażę konkretny plik. Nie zakładaj, że projekt już działa ani że każdy uczestnik ma ten sam stan repozytorium.

Jeśli wybór bibliotek, architektury lub sposobu uruchomienia nie został jeszcze rozstrzygnięty, wypisz potrzebne decyzje. Sprawdź aktualną dokumentację oficjalną z datą lub wersją, porównaj rozsądne opcje i zaproponuj użycie zainstalowanej umiejętności `write-adr`. Oddziel fakty potwierdzone od założeń. Dla niezależnych decyzji zaproponuj oddzielne ADR-y; nie wymyślaj ich treści przed moją decyzją.

Przygotuj **plan, bez implementowania go teraz**. Podczas warsztatu chcemy przejść cały proces na jednym niewielkim fragmencie, bez obietnicy ukończenia całej aplikacji. Pokaż, jak użyłbyś trybu Plan, i czym różni się plan zapisany w zwykłej sesji: co możesz tam tylko opisać, a co wymaga mojej zgody przed edycją. Jeśli brakuje kluczowych danych, zadaj najpierw kilka konkretnych pytań zamiast zgadywać.

Zwróć:
1. Jednozdaniowy cel najbliższego fragmentu z PRD, zakres poza zadaniem i kryteria akceptacji możliwe do sprawdzenia.
2. Fazy: rozpoznanie stanu → ewentualne ADR → plan → test, który początkowo nie przechodzi → niewielka implementacja → testy i kontrola ręczna w przeglądarce, jeśli jest UI → pokaz grupie → poprawka rzeczywistego problemu → niezależny przegląd → pull request tylko dla gotowego fragmentu.
3. **Macierz zadań i zależności**. Dla każdego wiersza podaj: identyfikator, wynik, zależności, właściciela, pliki lub obszar własności, kryterium ukończenia, test albo inny dowód, punkt kontroli człowieka i możliwy następny krok. Oznacz, co da się robić równolegle, a co trzeba wykonać po kolei.
4. Propozycję delegowania wyłącznie niezależnych zadań. Porównaj jednego agenta z subagentami domyślnymi, doraźnymi i własnymi; dla każdego delegowanego zadania przygotuj krótki, wystarczający brief i granice plików. Nie zakładaj, że wszystkie rodzaje subagentów są dostępne w moim wydaniu Copilota. Wskaż ryzyko konfliktów przy wspólnym katalogu i kiedy osobne worktree lub sesje byłyby użyteczne, a kiedy zwiększają narzut.
5. Jeden wspólny sposób śledzenia stanu pracy w zespole (np. GitHub Issues, Jira, Linear albo Beads, jeśli już go używamy). Nie twórz równoległych źródeł prawdy bez potrzeby. Pokaż przekazanie zadania między agentami i sposób scalenia wyników przed testami całości.
6. Plan kontroli jakości: testy lokalne, kontrola działania aplikacji przez agenta i człowieka, przegląd zmian, reakcja na uwagi z code review, dokumentacja wyników. Oddziel wynik faktycznie sprawdzony od deklaracji agenta.
7. Plan awaryjny, jeśli zabraknie czasu, dostępu, przeglądarki lub kredytów AI: najmniejszy pokaz możliwy do wykonania z istniejącym kodem i jasny zapis pracy do dokończenia.

Zapisz plan jako dokument tylko w miejscu, które wskażę lub zatwierdzę. Poza tym dokumentem nie modyfikuj plików; nie implementuj funkcji, nie twórz gałęzi, issue ani pull requesta i nie uruchamiaj delegowanych agentów, dopóki nie przejrzę planu. Nie narzucaj z góry konkretnego języka, frameworka, liczby agentów ani nazw plików, których nie ma w projekcie. Na końcu wskaż trzy najważniejsze decyzje, które mam zatwierdzić przed rozpoczęciem pracy.
03 / podział pracy

Deleguj według macierzy zależności

  • Zlecaj równolegle tylko zadania z oddzielnymi plikami i jasnym wynikiem. Każdy agent dostaje cel, zakres, sposób sprawdzenia i informację o pracy pozostałych.
  • Jeden katalog: przypisz właścicieli plików i ustal kolejność zależności. Jeden agent integruje wyniki i uruchamia testy całości.
  • Worktree: ogranicza konflikty, ale wymaga osobnych zależności, serwera i późniejszego scalenia.
03 / sesje i role

Równoległość wymaga wspólnego stanu

  • Copilot CLI: ← otwiera panel sesji (przy pustym polu), a /session kartę wszystkich sesji (dokumentacja).
  • Subagenci: zacznij od roli doraźnej; własną konfigurację utwórz dla powtarzalnych zadań lub innych uprawnień.
  • Do zarządzania wieloma trwałymi procesami agentów możesz użyć Herdr.
  • Wspólny stan: Beads lub plik Markdown/JSON; Linear do zadań zespołu.
04 / implementacja

Mały fragment, test przed kodem

  • Wybierz jedną funkcję z PRD i ustal mierzalne kryterium zaliczenia.
  • Agent dodaje lub uruchamia test, który ujawnia brak zachowania - nie zmieniaj asercji, żeby uzyskać pozorny zielony wynik.
  • Agent wdraża najmniejszą potrzebną zmianę i uruchamia testy fragmentu, a potem testy całości.
  • Ty ustalasz zakres, przeglądasz diff, sprawdzasz zgodność z ADR i zatwierdzasz wynik.
05 / sprawdzenie w praktyce

Pokaż działanie i napraw prawdziwy błąd

Poproś agenta o przejście rzeczywistego przepływu. Jeśli aplikacja ma UI, niech użyje Playwright lub Chrome DevTools i pokaże zrzut oraz wynik nawigacji klawiaturą.

  • Sprawdź też ręcznie najważniejszą ścieżkę użytkownika.
  • Wybierz błąd lub rozbieżność z PRD, zlec poprawkę agentowi i uruchom testy ponownie.
  • Jeśli skończy się czas lub kredyty - zapisz stan, testy i następny krok.
06 / współpraca przez GitHub

Pull request dopiero po lokalnym sprawdzeniu

Zakończ fragment, uruchom testy, poproś drugiego agenta o niezależny lokalny przegląd. Oceń uwagi, popraw, sprawdź ponownie - dopiero potem wypchnij gałąź.

  • Opisz PR i dołącz wyniki testów oraz krótką demonstrację.
  • Przejrzyj uwagi człowieka i Copilot code review. Weryfikuj każdą uwagę przed zmianą kodu i ponów testy.
  • Scalaj dopiero gdy zmiana jest gotowa i zaakceptowana.
07 / dalsza praktyka

Sprawdź zasady i wybierz dalszy krok

  • Pracujesz z kodem firmowym? Sprawdź zasady ochrony danych i dostępne funkcje Copilota w swojej organizacji.
  • Chcesz przećwiczyć pracę z kodem legacy? Poznaj publiczny projekt JFTP.
  • Zobacz też odpowiedzi na pytania z kursu.
08 / pytania z kursu

Wasze pytania: krótkie odpowiedzi

  • Agent Host i WSL: połącz VS Code z WSL, a agent działa w Linuksie. Assisted permissions są tylko w Agent Host.
  • Worktrees z pnpm: virtualStoreType: global i kolejny worktree instaluje się w kilka sekund.
  • Hooki: matcher, if albo skrypt zawężają hook do plików i poleceń. Blokada sekretów dla Copilota, Claude Code i Codex.
  • Agent w CI/CD: code review i security review w Azure, GitLab i Bitbucket, z komentarzem w Jira. Gotowe pipeline'y.
  • Indeks kodu: Copilot ma wyszukiwanie semantyczne jak Cursor; agent używa go sam, ręcznie przez #codebase.
  • Session Sync: ikona Copilota w prawym dolnym rogu i Session Sync: Enable.

Czym jest MCP

MCP łączy agenta z zewnętrznymi narzędziami.

Jak działa

Moduł 2.1 / ważny trend

CLI i MCP: koszty oraz korzyści

MCP

  • Gotowa integracja udostępnia agentowi narzędzia.
  • Wymaga konfiguracji i kontroli dostępu.

CLI

  • Agent uruchamia polecenie, gdy jest potrzebne.
  • Łatwo sprawdzić wejście, wyjście i błędy.
Coraz częściej wybieramy CLI: mniej tokenów w kontekście i prostsze debugowanie. MCP zostaje tam, gdzie nie ma dobrego CLI.

  • Serwer MCP udostępnia skille, agent pobiera je na żądanie.
  • Zawsze aktualna wersja, bez ręcznej aktualizacji w każdym repozytorium.

Moduł 2.4 / TDD

TDD z agentem: Red-Green-Refactor

Cykl TDD

1
Red: test ujawnia brak zachowania.
2
Green: najmniejsza zmiana daje zielony test.
3
Refactor: popraw kod bez zmiany zachowania.

Sprawdź z agentem

  • Test sprawdza wynik, nie sposób implementacji.
  • Uruchom test po każdym kroku.
  • Przed zmianą upewnij się, że test potrafi wykryć błąd.
Moduł 2.4 / wymóg

Małe commity po sprawdzonych zmianach

Dobra historia

  • Jeden spójny, sprawdzony fragment na commit.
  • Test i kod mogą trafić do tego samego działającego commitu.

Unikaj

  • Jednego commitu ze wszystkim na koniec.
  • Łączenia niezależnych zmian.
  • Commitu bez uruchomionych testów.
Test ręczny

Agent przechodzi przez rzeczywisty przepływ

  • Agent otwiera stronę lub CLI i wykonuje scenariusz jak użytkownik - sprawdza stan pusty, błąd i poprawne zgłoszenie.
  • Jeśli jest UI: agent zbiera zrzut, dane z DOM, wynik nawigacji klawiaturą i komunikaty.
  • Porównuje zachowanie z wymaganiami; rozbieżności zapisuje z krokami odtworzenia.
  • Integracje płatne lub zewnętrzne testuj tylko w kontrolowanym środowisku.
Copilot / opcjonalnie

Delegowanie tylko przy niezależnych zadaniach

Najpierw ustal kontrakt, właściciela plików i test dla każdej części.

  • Nie przypisuj dwóch wykonawców do tego samego pliku.
  • Każdy wynik wymaga weryfikacji w głównej zmianie.
Dodatkowy prompt / plan

Krótszy plan dla małego zadania

Dla małej zmiany możesz użyć krótszego promptu do planowania: 3-5 zadań na podstawie aktualnego PRD. Przy większym projekcie skorzystaj z planu z macierzą zależności.

Plan zespołu agentów

Plan one small feature from the PRD the user has approved for this application: either the group project or the participant's own idea. Give each task a clear owner, file boundary, handoff and check. Confirm the current tool supports parallel agents before proposing them.

Locate the current approved PRD in this application project; if several candidate PRDs exist, ask which one governs before planning. Read all relevant approved ADRs and design guidance, if any, then inspect the current code and tests. Do not treat PRD or ADR examples in `course-materials/` as project decisions unless the user explicitly names one for this task. Choose **one vertical slice** that can be demonstrated through a user-visible or API-visible result. Do not plan the entire application at once. Resolve the acceptance criterion, the starting state, the smallest files likely to change, and the commands or observable checks that prove completion. If any of those are unclear, list targeted questions before work begins.

Produce a table with 3-5 tasks. For each task include: ID, deliverable, input/context files, owner role, files it may edit, dependency, verification command/check, and a concrete Definition of Done. Mark which tasks are sequential and which could proceed independently. If the tool supports sub-agents and isolated worktrees, propose how to assign independent tasks without overlapping files. If it does not, use the same table as a single-agent checklist; do not fabricate sub-agent commands.

Make testing a real dependency: a test or observable baseline precedes implementation, an integration check follows the affected components, and a final diff/review follows all changes. Keep commits small and meaningful after a green phase. The plan must state how to handle a failed test, an unexpected existing change, a version/API mismatch, and an external model unavailable during the lab. Protect existing work and avoid destructive reset commands.

Stop at the plan. Return the dependency matrix, a one-paragraph critical path, and the first bounded task ready for a developer or coding agent. If the user has approved a destination path, save the complete plan there as a reviewable document. Otherwise propose a path and ask before writing the file; still return the draft in the response. Creating the plan document is allowed, but do not implement code, start delegation, open a pull request or merge anything until the user has reviewed the plan and explicitly asks to proceed.
Zespół agentów

Kiedy delegować, kiedy zostać przy jednym

  • Rozdziel zadania z niezależnymi plikami i kryteriami wyniku.
  • Główny agent uzgadnia interfejsy, zbiera wyniki i uruchamia testy całego przepływu.
  • Nie deleguj współdzielonego pliku dwóm wykonawcom bez kontraktu.
  • Każdy wynik ma listę zmian, testów i ryzyk.

Dane / pełny prompt

Syntetyczne dane i testy

Skopiuj prompt poniżej lub otwórz plik Markdown albo bibliotekę promptów.

Analiza danych syntetycznych

Pracuj wyłącznie na syntetycznych plikach z repozytorium kursowego: `course-materials/exercise-data/csv/complaints.csv` i `course-materials/exercise-data/csv/products.csv`. Pracujemy **dopiero po ukończeniu i przeglądzie głównej aplikacji kursowej**. Otwórz we własnej kopii projekt JFTP wskazany w materiale źródłowym: https://github.com/sai-pullabhotla/jftp. Pracuj w GitHub Copilot w udostępnionym środowisku. Nie łącz aplikacji z cudzym serwerem FTP ani nie używaj prawdziwych danych uwierzytelniających.

**Etap 1 - rozpoznanie, bez edycji.** Przeczytaj README, konfigurację budowania, strukturę katalogów i reprezentatywne pliki startowe, UI, logiki FTP oraz zależności. **Etap 2 - uruchomienie minimalnym kosztem.** Po mojej zgodzie ustal dostępne lokalnie JDK i narzędzie budowania, uruchom istniejące polecenia, zachowaj dokładny błąd oraz odróżnij problem środowiska od błędu kodu. Dobierz framework testowy dopiero po sprawdzeniu wersji Javy i systemu budowania. Pokaż czerwony wynik dla wykrytej luki lub zielony baseline dla zachowania już działającego; wyjaśnij, czego te testy **nie** pokrywają. Nie obiecuj pełnego pokrycia w tym ćwiczeniu.

**Etap 4 - jeden bezpieczny krok modernizacji.** Gdy aplikacja uruchamia się na tyle, by sprawdzić wybrany przepływ, a testy dają użyteczny punkt odniesienia, zaproponuj jedną małą aktualizację Javy, zależności albo refaktoryzację bez zamierzonej zmiany funkcji. Przed edycją pokaż zgodność, ryzyko, pliki w zakresie, komendę weryfikacji i sposób cofnięcia. Po zmianie uruchom te same testy i krótki test ręczny aplikacji, porównaj wyniki z baseline i pokaż diff. Jeśli test przestanie przechodzić, najpierw podejrzewaj zmianę kodu, a nie poprawiaj asercji dla zielonego wyniku.

Na koniec zwróć: mapę projektu, rzeczywiście uruchomione polecenia i wyniki, listę dodanych testów, mały diff, ograniczenia oraz następne kroki. To pokaz metody pracy z legacy; **nie** twierdź, że cały JFTP został zmodernizowany. Jeśli czas kursu się skończy, zakończ po dowolnym etapie, zostaw odtwarzalny checkpoint i plan jako pracę własną.

Test schematu nie zastępuje testu reguły
