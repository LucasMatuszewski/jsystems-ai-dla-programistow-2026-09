Biblioteka opcjonalna

Tryby pracy z agentem

Terminal, IDE i interfejs webowy

W terminalu agent widzi pliki i komendy dostępne w bieżącym katalogu; w IDE szybciej przełączasz się między edycją a podglądem diffu; w interfejsie webowym zakres narzędzi i uprawnień zależy od usługi. Dla tego samego zadania zachowaj semantykę: cel, pliki wejściowe, granice zmian, dowód wyniku. Nie przenoś bezmyślnie flag CLI, nazw modeli ani plików konfiguracyjnych między Copilot, Claude Code i Codex. Sprawdź aktualną dokumentację instalacji i uprawnienia środowiska przed ćwiczeniem.

Biblioteka opcjonalna

Kontekst i sesja

Jak agent wie, nad czym pracuje

Pliki repozytorium, instrukcje projektu, historia rozmowy i wyniki narzędzi składają się na kontekst. Długi czat nie jest trwałą dokumentacją projektu. Stabilne reguły zapisz w wersjonowanych instrukcjach, a decyzję techniczną w ADR. Przy wznowieniu pracy przekaż stan repozytorium, wykonane testy, otwarte pytania i następny mały krok. Kiedy model gubi szczegóły, nie dodawaj większego bloku ogólnego tekstu: wskaż właściwe pliki oraz kryterium wyniku.

Biblioteka opcjonalna

Uprawnienia

Granice dla poleceń i danych

Zanim agent użyje terminala lub integracji, określ dozwolone katalogi, dostęp sieciowy, dane syntetyczne i działania wymagające zgody. Odczyt dokumentacji to inne ryzyko niż zapis do repozytorium lub wykonanie migracji. Dla baz używaj kopii lub użytkownika tylko do odczytu; nie testuj na produkcji. Weryfikuj faktyczne uprawnienia narzędzia, nie tylko prośbę zapisaną w promptcie. Zapisz wyniki skanu zmian przed commitem.

Biblioteka opcjonalna

Gałęzie i izolacja

Bezpieczne eksperymenty w Git

Oddziel ćwiczenie od głównej gałęzi. Zmiana ma mały zakres i czytelną historię: test, minimalna implementacja, refaktoryzacja. Worktree lub osobna gałąź pomaga równoległym zadaniom, ale współdzielone API i pliki wymagają kontraktu. Przed integracją sprawdź status, konflikt, diff i testy całego przepływu. Granularny commit oznacza spójną, zweryfikowaną zmianę, a nie każde zapisanie pliku.

Biblioteka opcjonalna

Dokumentacja jako kod

PRD, ADR i plan

PRD mówi, jakie zachowanie ma powstać i jak je rozpoznać. ADR zapisuje wybór techniczny oraz konsekwencje. Plan opisuje kolejność konkretnej pracy, właścicieli plików i punkty kontrolne. Wszystkie trzy mogą być Markdown w repozytorium, z historią i linkami do testów. Nie zastępują się nawzajem. Unikaj utrwalania hipotezy jako faktu; oznacz pytania do użytkownika. Pełne prompty PRD (P01) i ADR (P02) uruchamiają publiczne skills, a nie powtarzają ich metody.

Biblioteka opcjonalna

MCP, CLI i skills

Dobór sposobu integracji

MCP jest interfejsem narzędzi agenta; CLI wykonuje jawne polecenia; skill opisuje wielokrokową procedurę i może zawierać skrypty. Narzut uruchomienia, poziom dostępu i możliwość powtórzenia testu różnią się między nimi. Wybierz najmniejszy zestaw potrzebny do zadania. Publiczne skills instaluj poleceniem skills CLI z zachowaniem pochodzenia; nie kopiuj folderów. Narzędzia zewnętrzne podłączaj dopiero po sprawdzeniu, jakie dane będą mogły odczytać.

Biblioteka opcjonalna

Przeglądarka i obraz

Dowód dla interfejsu

Zrzut ekranu może przekazać układ, kolory i stany, lecz drobny tekst oraz semantyka mogą być błędnie odczytane. Dlatego porównuj obraz z DOM, strukturą nagłówków i nawigacją klawiaturą. Przy odtwarzaniu systemu wizualnego wydziel tokeny koloru, typografii i odstępów, a następnie sprawdź je na kilku ekranach. Dostęp do cudzego serwisu i użycie jego zasobów muszą mieścić się w uprawnieniach zadania. Pełny prompt P05 prowadzi tę analizę.

Biblioteka opcjonalna

Testy od czerwonego

Warstwy weryfikacji

Test jednostkowy chroni mały kontrakt; integracyjny sprawdza współpracę komponentów; test przepływu bada zadanie użytkownika. Zacznij od testu, który ujawnia brak funkcji. Zmiana testu po niepowodzeniu wymaga dowodu, że kryterium było błędne. Po zielonym wyniku przeczytaj diff i sprawdź przypadek brzegowy. Przy zależności od płatnego modelu oddziel powtarzalne testy lokalne od kontrolowanych prób na żywej usłudze.

Biblioteka opcjonalna

Zespół agentów

Podział i integracja

Deleguj wtedy, gdy prace mają oddzielne pliki i jawny kontrakt wejścia/wyjścia. Ekspert od danych może przygotować schemat, ekspert od API endpoint, a recenzent niezależnie sprawdzić kryteria. Orkiestrator uzgadnia interfejsy i integruje wyniki; nie zakłada, że raport wykonawcy zastępuje test. Wspólny plik albo nieuzgodniona migracja może zniweczyć korzyści równoległości. P04 zawiera gotową macierz zależności.

Biblioteka opcjonalna

Praca na danych

SQL, Pandas i większe zbiory

Na syntetycznych danych można przećwiczyć jakość, klucze, brakujące wartości, agregację i interpretację. Każda metryka potrzebuje jawnego mianownika. Wynik SQL zweryfikuj drugim, niezależnym zapytaniem lub skryptem. Przy większych danych sprawdź plan zapytania, indeksy, koszt przeniesienia danych oraz zgodność wyniku po zmianie silnika. Nie nazywaj liczby zdarzeń wskaźnikiem bez odpowiedniej ekspozycji. P06 i P09 używają małych, offline plików CSV.

Biblioteka opcjonalna

Kod legacy

Najpierw zachowanie, potem migracja

Stary projekt może nie uruchamiać się z powodu środowiska, a nie błędu logiki. Zmapuj zależności, punkty wejścia, stan i zewnętrzne systemy. Testy charakterystyki zabezpieczają obserwowalne działanie przed zmianą wersji bibliotek. Aktualizuj w małych etapach, sprawdzaj zgodność i utrzymuj punkt cofnięcia. P07 opisuje plan dokumentacji, testów, minimalnego startu i modernizacji bez dodawania funkcji.

Biblioteka opcjonalna

Automatyzacja po warsztacie

Powtarzalny proces bez ukrytego ryzyka

Jeśli zadanie wraca, zamień sprawdzoną procedurę w skill albo skrypt, z wejściem, wyjściem i testem. W CI stosuj ograniczony zakres uprawnień i przegląd zmian przed publikacją. Harmonogram lub tryb headless nie naprawia niejasnych kryteriów. Najpierw uruchom proces ręcznie i zapisz dowód, potem automatyzuj. Przed każdym wdrożeniem sprawdź aktualne komendy konkretnego narzędzia.
